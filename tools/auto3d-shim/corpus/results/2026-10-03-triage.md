## The two FAILs (threejs-journey, bruno-simon): not harm

Evidence, from both runs:

- `engineOracle` is `three.js r185` / `r183`, and `webglContexts` is 0 in both loads.
- Our logs: `three.js adapter armed`, then `[warn] WebGPURenderer seen — not converted by this prototype, left 2D`.
- No timers from our scripts, no exceptions, no new console errors, no surface diff beyond `getContext` / `__THREE_DEVTOOLS__`.
- fps is 61/60 and 60/60.
- The injected screenshots show both pages fully rendered, the same as the control.

Three r183+ announces itself through `__THREE_DEVTOOLS__` at module load, so the sentinel loads the core, as designed for a three.js page. The page then renders with `WebGPURenderer`, which calls `canvas.getContext('webgpu')`, and the PROBE only counts `/webgl/`. So the rule "core loaded on a page with no WebGL" (the §3.3 no-engine rule, meant for plain pages) fires on a page that has an engine and a GPU canvas.

- **H3, harness fix (`run-corpus.mjs`):**
  - In `PROBE`'s `getContext` wrapper, count WebGPU separately: `if (r && /webgpu/i.test(String(type))) webgpu++`. Return `webgpu` from `read()`.
  - In `judge()`, define `const gpu = webgl || (P.webgpu || 0) > 0 || (Q && Q.webgpu > 0)`. Use `gpu` instead of `webgl` for the "no-WebGL page" timer / `loadCore` FAIL rules (and for the `allowedKeysWebGL` choice).
  - Alternatively, exempt a page whose control `engineOracle` already names three.js / PlayCanvas.
- **G1, shim reporting gap (follow-up, not done here):**
  - File: `tools/auto3d-shim/three-adapter.js`, `onObserve`. The `o.isWebGPURenderer` branch only calls `warnOnce(...)` and returns. No state carries a `flatReason`, so `core.js` `statusOf()` falls through to `{ status: 'idle' }` with no reason. The README's engine pass is "`flat (reason)`".
  - Fix: mirror `playcanvas-adapter.js:189/272`, which reports WebGPU as `flat` with "WebGPU device — the prototype drives WebGL2 apps only". In the WebGPU branch, when `o.domElement instanceof HTMLCanvasElement`, record a flat note: `const st = core.newState('three.js', o.domElement, ad); st.flatReason = 'WebGPURenderer — the prototype drives WebGL only'; core.notify();`. Do this without `wrap(st)`, so nothing on the renderer is touched.
  - Check first that a bare `newState` is not picked up by the activation loop. If it is, add a small `core.noteFlat(engine, canvas, reason)` that pushes such a state into `tracked` and does nothing else.
  - The outcome then reads `flat (WebGPURenderer…)`.
  - github-home (`not converting yet: the screen camera is not a PerspectiveCamera`) also reports a bare `idle`. That one is a "not yet" rather than a "never", so leaving it `idle` is defensible, but the host then gets no reason for a 2D three.js page.

## Recurring REVIEW causes

**H1: the injected load's console listener stays attached through the 3 warm reloads; the control load has no reloads.**
`load()` collects `console`/`pageerror` for the whole life of the page. Only the injected load then reloads 3 times for the warm cost. A standalone test with **no product at all** (fake-xr only, then the same 3 reloads) reproduces the "injected-only" errors, and they appear only in the reload phases:

- reddit: `Not signed in with the identity provider.` on reload 1-3
- notion: reload 2-3
- stackoverflow: reload 1-3, plus `[GSI_LOGGER]: FedCM get() rejects with NetworkError`
- etsy: `Failed to load resource: 403` on reload 1-3

Harness fix (`run-corpus.mjs`, `load()`): judge errors from the same window in both loads. Before the `if (injected) { out.warm = [] … }` block, record `const nE = out.errors.length, nP = out.pageErrors.length`. After the reload loop, move the reload-phase entries aside with `out.warmErrors = out.errors.splice(nE); out.warmPageErrors = out.pageErrors.splice(nP);`. Keep those for information; do not judge them. Also detach or ignore `ourLogs` from the reloads, so `row.ourLogs` describes the first load. With H1 fixed, reddit, notion and etsy would most likely PASS.

**H2: "Blocked script execution in 'about:blank' because the document's frame is sandboxed and the 'allow-scripts' permission is not set."**
This appeared on youtube, cnn, stackoverflow, ebay, spotify, cesium and unity-play, in 3/3 runs on each. A local page with sandboxed about:blank iframes, plus bisection, shows the mechanism:

- CDP `Page.addScriptToEvaluateOnNewDocument` scripts **do run inside same-process sandboxed no-script about:blank frames**.
- Any callback those scripts register (a no-op `readystatechange` listener alone reproduces it: 6 messages) is then blocked when it fires, and Chrome logs that message per firing.
- Results on the test page:
  - control (fake-xr): 0 messages
  - control + the PROBE: also produces it on ikea
  - injected: 9 messages
  - `engines.playcanvas: false`: 0 messages; the PlayCanvas route's `readystatechange` listener + MutationObserver is what fires in those frames
  - the same scripts gated on `window === top`: 0 messages

It is console noise only. It is not page-observable, and our code does nothing in those frames, since none of it can run there.

- **Harness fix:** wrap the PRODUCT strings in `if (window === top) { … }`. That matches README "Only the main frame is covered". Do the same for the PROBE, or the probe itself causes the message.
- **Browser follow-up (not verifiable from this repo):** check that the DisplayXR Browser's main-world injector skips frames whose sandbox flags disallow scripts (sandboxed without `allow-scripts`). If it injects there the way CDP does, real users get this message in DevTools on ad-heavy pages. The fix would go in the injector, not the shim: a sentinel in an opaque-origin sandboxed frame cannot reliably detect its own sandbox.

**G2: "our MutationObserver spent > 5 ms"** on guardian, cnn, stackoverflow, ebay, ikea, outlook-login, booking, babylon-playground and webgl-aquarium. The figures are stable across runs: 5.5 to 13.4 ms in total.

- This is the sentinel's parse-time observer (`sentinel.js` `observe()` / `onMutations()`). It lives from document start until load + 10 s.
- Each callback reads one cached live `getElementsByTagName('canvas')` collection, so the cost is per mutation batch, and ad-heavy pages that load slowly fire many batches.
- The total sits under no §3.3 FAIL rule. 5 ms is a REVIEW threshold. Whether this is a real gap cannot be decided from the data: `row.moMs` is a sum, and the runner discards `mo.calls`. With `performance.now()` clamped to 0.1 ms, the per-callback cost is not recoverable.
- **Disposition: (c) open question, not a bug.** Next step: in `judge()`, keep `mo.calls` and a max-per-callback figure in the row (the PROBE already counts `calls`; add `max`). Re-run these 9 sites, then judge per callback, against frame budget.
- If the per-callback cost turns out to be non-trivial, a shim-side option is to end the observer at `DOMContentLoaded` + N s instead of load + 10 s on pages that have no `<canvas>` by then. That is a behaviour change for late-canvas PlayCanvas pages, so it needs its own test case.

**outlook-login FAIL in re-run 2 (A/B variant):**

- What changed: `Element.animate` and `Element.attachShadow`, in the same load as the Adobe Target globals `ttMETA`, `m365TargetTools`, `targetActivityID/Variant/Name/Title`, `__clr`.
- Not our code:
  - The bundle never writes either property; `grep animate dist/*` finds 0 hits. The sentinel only *reads* `Element.prototype.attachShadow` into its frozen intrinsics.
  - `loadCore` was 0, so the core never ran.
- 8 standalone loads (4 control, 4 injected, PROBE included) were never served the Target variant, and none had the change.
- So it travels with the A/B variant. Two control loads in the corpus run were not enough to subtract it.

**E1: `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`** on twitch.tv and playcanv.as (both PlayCanvas-hosted projects):

- It reproduces in plain headless Chrome 154 with only `--no-sandbox`.
- curl (schannel) gets HTTP 200 from both hosts.
- The same Chrome reaches superspl.at.
- So it is a Chrome-to-CDN TLS issue on this box or network, not a property of the sites or of us.
- Not verified: whether a headed Chrome on this box reaches them. David's Chrome was deliberately not used.
- Before replacing the sites, re-run them from another box. If they fail there too, swap in a different `playcanv.as` / twitch-like URL.
